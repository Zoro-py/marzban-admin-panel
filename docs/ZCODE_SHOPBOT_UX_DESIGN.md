| آرکتایپ | کجاست | چه می‌خواهد (شغل) | از چه می‌ترسد |
|---|---|---|---|
| **نوآمد** | تازه وارد چت شده، روی گوشی | تست رایگان یا اولین سرویس را همین حالا بگیرد و وصل شود | «کلاهبرداری است؟ پولم می‌رود؟»؛ «سخت است، بلد نیستم» |

## ۲. حقایق سِروِر که طراحی باید آینه کند

- **VERIFIED — سفارش اول، پرداخت بعد** (docstring ماژول shop.py): مشتری حجم را انتخاب می‌کند بی‌آنکه پولی بدهد؛ رسیدِ بعدی یک عددِ دقیق دارد.
- **VERIFIED — «خرید» برای مشتریِ فعلی = تمدید** (extend)؛ سرویسِ جداگانه با `force_new_service` مسیرِ جدا است (`shop.py:520-550`).
- **VERIFIED — بدهی خرید را می‌بندد**: متنِ `debt_status` می‌گوید «تا وقتی بدهی پرداخت نشود، خرید سرویس جدید ممکن نیست» و ردِ `DEBT_LINE:` روی پرداختِ کیف‌پولی هم می‌آید (`shop.py:795`).
- **VERIFIED — پرچم‌های منو هر بار از سشن می‌آیند**: `trial_available`, `balance`, `ledger_debt`, `payg_enabled` (`shop.py:174-205`) — منوی زمینه‌ای بدون کش ممکن است.
- **VERIFIED — تحویل (QR+لینک+راهنما) پوشِ بک‌اند است** و برای خریدِ کیف‌پولی و کارت‌به‌کارت یکسان (`shop_texts.py` docstring).
- **VERIFIED — رسید = عکس، فایلِ تصویری، یا کدِ تایپی**؛ PDF رد می‌شود (`shop.py:920-934`).
- **VERIFIED — دکمه‌های «🔄 تمدید همین سرویس» و «⚡ تمدید خودکار» پوشِ بک‌اند روی هشدارهاست** (`shop_service.py:1708,1719`).
- **VERIFIED — سؤال نام کاربری فقط وقتی سفارش سرویسِ نو می‌سازد** (`creates_new`, `shop.py:707`).
- **VERIFIED — F10**: کسری زیر کفِ شارژ → عددِ کف پرسیده می‌شود و مازاد به کیف‌پول برمی‌گردد.
- **ASSUMED — تغییرِ برچسبِ دکمه‌های منو تست‌ها را نمی‌شکند**: تست‌ها به ثابت‌های `texts.MENU_*` رجوع می‌کنند، نه به مقدار رشته (وریفای شد در `test_prepublic_p0p1_bot.py`/`test_shop_link_claim.py`). تغییرِ مقدارِ ثابت امن است.
- **ASSUMED — عددِ رویِ برچسبِ دکمه (مبلغ بدهی) قابل قبول است**: دکمه‌های reply keyboard مقدارِ داینامیک می‌پذیرند؛ منو از قبل زمینه‌ای است. (اگر مالک نخواهد، برگشت به برچسب ثابت — سؤالِ بازِ تهِ سند.)

## ۳. فرکانس → جایگاه

| عمل | فرکانس | جایگاه جدید |
|---|---|---|
| دیدن مصرف/وضعیت | روزانه–هفتگی (لحظهٔ قطعی) | دکمهٔ سطح بالای «سرویس‌های من»؛ خودِ کارت همه‌چیز را نشان می‌دهد |
| تمدید | ماهانه؛ اضطراری هنگام هشدار | دکمهٔ «تمدید» روی خودِ کارت + دکمهٔ پوشِ هشدار (موجود) |
| خرید | ماهانه | دکمهٔ سطح بالای «خرید / تمدید» |
| شارژ/پرداخت بدهی | هفتگی–ماهانه؛ برای بدهکار فوری | یک درِ «حساب من» — برای بدهکار، برچسبش خودِ عددِ بدهی است |
| سرویسِ جداگانه، سرویسِ مصرفی | نادر / یک‌بار | داخل صفحهٔ خرید (دکمه‌های همان صفحه) |
| راهنما، پشتیبانی | نادر | یک درِ «راهنما و پشتیبانی» |

## ۴. سه طرحِ منو (موکاپ متنی) و انتخاب

### طرح A — «سه در» (پیشنهاد)

مشتریِ عادی با کیف‌پول:

```
🛒 خرید / تمدید            📱 سرویس‌های من
💳 حساب من
❓ راهنما و پشتیبانی
```

نوآمدِ واجدِ تست (کیف/بدهی ندارد؛ «حساب من» پنهان — همان منطقِ فعلیِ مخفی‌کردنِ کیف‌پول از غریبه):

```
🎁 تست رایگان
🛒 خرید سرویس
❓ راهنما و پشتیبانی
```

بدهکار (عدد روی خودِ دکمه):

```
🛒 خرید / تمدید            📱 سرویس‌های من
💳 ماندهٔ پرداخت: ۱۲۳,۰۰۰ تومان
❓ راهنما و پشتیبانی
```

- سطح بالا: حداکثر ۴ دکمه (بدترین حالتِ نوآمد) و ۴ دکمه برای همهٔ بقیه — از ۱۰ دکمهٔ فعلی.
- «سرویسِ جداگانه» و «سرویسِ مصرفی» → دکمه‌های صفحهٔ خرید؛ «کیف پول»، «شارژ»، «پرداخت بدهی» → یکی شد: «حساب من»؛ «راهنما» و «پشتیبانی» → یکی شد.

### طرح B — «ردیفِ پولِ جدا»

```
🛒 خرید / تمدید
📱 سرویس‌های من            💳 حساب من
❓ راهنما و پشتیبانی
```

محتوایش با A یکی است؛ فقط چیدمان. «حساب من» کنارِ «سرویس‌های من» یعنی دو عملِ پربسامدِ هم‌عرض؛ برای بدهکار، عددِ بدهی در ردیفِ دوم کمتر به چشم می‌آید.

### طرح C — «داشبورد» (منو = سرویس‌های من)

```
📱 سرویس‌های من            💳 حساب من
❓ راهنما و پشتیبانی
```

/start برای مشتریِ فعلی خودِ لیستِ سرویس‌ها را می‌فرستد و خرید/تمدید فقط روی کارت‌هاست. سریع‌ترین مسیر برای تمدید، ولی نوآمد به صفحهٔ خالیِ «هنوز سرویسی نگرفته‌اید» می‌رسد و مسیرِ نوآمد (مهم‌ترین مسیرِ رشد) قربانی می‌شود؛ تغییرِ رفتارِ /start هم بزرگ‌ترین ریسکِ رگرسیون را دارد.

### انتخاب: **طرح A** — با دلایل

1. هر سه هدفِ سخت را می‌گیرد: خرید ≤۳ (بندهٔ ۶)، تمدید از کارت ۱ تپ (بندهٔ ۶)، بدهی ≤۲ (بندهٔ ۶) — بدون دست‌زدن به رفتارِ /start.
2. بدهکار عدد را روی منو می‌بیند (یک نگاه = جوابِ «الان چه‌کار کنم؟») و راهِ پرداختش ۲ تپ است؛ برای او این فقط منو نیست، پاسخ است.
3. نوآمد سه دکمه می‌بیند و اولیِ آن‌ها «تست رایگان» است — کوچک‌ترین صفحهٔ تصمیم ممکن.
4. طرح C را رد کردم چون مسیرِ نوآمد را بدتر می‌کند و /start را برای یک بهبودِ حاشیه‌ای بازنویسی می‌کند؛ مزیتش (تمدید سریع‌تر) را طرح A با دکمهٔ روی کارت می‌گیرد.
5. طرح B را رد کردم چون تنها تفاوتش با A، کمتر-به-چشم-آمدنِ بدهی برای بدهکار است — دقیقاً وارونهٔ منفعت.

| ۶ | دیدن مصرف | ۱ → **۱** (۰ تپ بعد از بازکردنِ کارت) | «سرویس‌های من» → N کارت؛ مصرف/روز/وضعیت روی خودِ کارت؛ خطِ کیف‌پولِ انتهایی حذف (جایش «حساب من») |

## ۶. تصمیم‌های طراحی با دلیل (قابلِ رد توسط مالک)

1. **«حساب من» یک عدد نشان می‌دهد، هرگز دو عدد کنارِ هم.** بدهکار: «ماندهٔ پرداخت‌نشده: X» + دکمهٔ پرداخت. مثبت: «موجودی شما: X» + دکمهٔ شارژ. صفر: «موجودی شما: صفر» + شارژ. جزئیاتِ per-account (بدهیِ هر حساب) فقط پشت «جزئیات» — هرگز پیش‌فرض.
2. **عددِ بدهی رویِ برچسبِ دکمهٔ منو.** منو از قبل زمینه‌ای است؛ این آخرین پلهٔ «یک نگاه، یک جواب» است. اگر مالک برچسبِ عدددار را نخواهد: برگشت به «💳 ماندهٔ پرداخت» ثابت — همه‌چیزِ دیگر سرِ جایش می‌ماند.
3. **حذفِ سؤالِ نام کاربری از مسیرِ اجباری خرید.** نامِ خودکار (`shop12`) برای ۹۵٪ کافی است؛ چیزی که مشتری واقعاً می‌بیند «نامِ سرویس» است که از قبل با ✏️ قابلِ تغییر است. عدهٔ خاص، دکمهٔ فرعیِ صفحهٔ حجم را می‌زنند. (مخالفِ F-E2 — دلیل: هزینهٔ یک تپ روی مسیرِ اکثریت، برای ابزارِ نادری که بعداً هم قابلِ جبران نیست.)
4. **دکمهٔ تمدیدِ روی کارت، تمدیدِ همان سرویس با همان حجمِ باقی‌ماندهٔ قرارداد** می‌سازد (رفتارِ extend فعلی) — صفحهٔ بعد، پرداخت. حجمِ دلخواه همچنان از «خرید».
5. **پرداختِ بدهی از کیف‌پول با همان دکمهٔ حاملِ مبلغ، یک‌تپی می‌شود** — ریسکِ تپِ اشتباه پایین است چون پول به حسابِ خودِ مشتری می‌رود و صفحه قبلش مبلغ را نشان داده. (مخالفِ تأییدِ دومفعلیِ فعلی؛ اگر مالک تاییدِ دوم را بخواهد، هدف ≤۲ فقط برای مسیرِ رسید برقرار می‌ماند.)
6. **پرامپت شماره تلفن، کیبورد را نمی‌بلعد**: زیر دکمه‌هایش ردیف‌های منو می‌آید (T7).
7. **واژه‌نامهٔ واحد** (T5): «حساب» برای پول، «سرویس» برای محصول، «شارژ» برای واریز، «ماندهٔ پرداخت» برای بدهی — «صورت‌حساب»، «لجر»، «payg»، «کیف‌پول/شارژ کیف‌پول/پرداخت بدهی به‌عنوان سه دکمه» حذف.

## ۷. سؤال باز از مالک (مسدودکننده نیست — پیش‌فرض ساخته می‌شود)

1. عددِ بدهی روی برچسبِ دکمهٔ منو — قبول است؟ (پیش‌فرض: بله)
2. پرداختِ بدهیِ کیف‌پولی یک‌تپی بدونِ تأییدِ دوم — قبول است؟ (پیش‌فرض: بله، مبلغ روی دکمه است)
3. حذفِ سؤالِ نام کاربری از مسیرِ اجباری خرید — قبول است؟ (پیش‌فرض: بله، با دکمهٔ فرعی روی صفحهٔ حجم)

## ۸. T5+T6 — جدول «قدیم ← جدید» برای ۲۵ متنِ پرتکرار (برای بازبینی مالک)

<div dir="rtl">

قدیم = نسخهٔ قبل از این راند (بیس `2b57db2`). جدید = وضعیت فعلی شاخه. سه ستون آخر: احساسِ ناخواسته‌ای که متنِ قدیم می‌توانست بسازد (چارچوبِ مهارتِ کپی فارسی).

| # | متن | قدیم | جدید | چرا |
