# Addendum 6 — dampen auto-queue package sizing against burst extrapolation (main @ b7238f0), deployed 2026-09-24 ~11:14 server time

**Owner report:** account "Benyamin" showed a 77 GB monthly-average while last month's actual bill was ~30 GB (150,000 T); investigated, found billing-correct/display-only (see below). Then: account "mansoorizade" showed **195 GB charged** while actual usage is ~20 GB — this one WAS a real, live, money-relevant bug.
**Rollback point:** `a36f30a` + backup `/app/data/pre_autoqueue_dampening_deploy_20260924_111332.db` (verified: 28.5 MB, 160 accounts, real data). No migration; backend-only (`sync_job.py`), no schema change.

## Benyamin (payg, id=39) — investigated, NOT part of this deploy
Billing was exactly correct (29.83 GB metered = 149,150 T). The dashboard's "Monthly average" briefly showed 77 GB because it was queried seconds after a manual settle reset the current-cycle baseline to "now" — `monthly_avg_usage()` fell back to a 72-day lifetime average dominated by an early heavy-usage burst in August. A 5-model council unanimously confirmed this read. No code changed for this account/case specifically — it surfaced the SAME underlying estimator weakness that caused mansoorizade's real bug below, which this deploy does fix (for the billing-consequential path only; the dashboard's display path is deliberately left as-is, see rationale below).

## mansoorizade (prepay, id=6) — the real bug
Full audit trail (`AccountEvent` log) showed exactly how: a 20 GB package was burned through in ~2.89 days (a one-time burst — the account's normal recent size was 20-50 GB packages). `_maybe_auto_queue_next_plan` fed that straight into `monthly_avg_usage()`, which linearly extrapolated the burst to "197.41 GB/month" with zero dampening, and auto-queued a **195 GB** next package — a 9.75× jump that would have billed **975,000 T** at settlement (was not yet billed — `billed_data_limit=0` — against a normal ~100-125,000 T bill). A fleet scan of the last 9 days' auto-queue events found the identical signature on a second account (id=71: 65 GB package burned fast → 228 GB/mo extrapolation → 225 GB queued, a 3.46× jump), confirming this is systemic, not a one-off.

**Immediate mitigation (same day, ahead of the code fix):** mansoorizade's live 195 GB package was manually downsized to 25 GB via the account's own `/adjust` endpoint logic (Marzban `modify_user` + local field sync only — verified this never touches `usage_baseline`/`used_traffic`/`billed_data_limit`, so nothing was billed by the action and the ~2 GB already consumed this cycle stayed correctly tracked). Confirmed via fresh DB read: `data_limit`=25.0 GB exactly, `used_traffic` unchanged, audit `AccountEvent` logged.

**Root-cause fix:** `backend/app/sync_job.py` — new `_dampened_package_size_gb()` applied between `monthly_avg_usage()`'s raw estimate and `_round_package_size()`: below `BILLING_MIN_CYCLE_DAYS=5.0` observed days, repeat the CURRENT package size instead of extrapolating at all (under-sizing self-heals via another renewal; over-sizing does not, it just bills for unused capacity); at or above that, cap growth at `MAX_GROWTH_MULTIPLE=2.0`× the current package size. The dashboard's `monthly_avg_usage()` itself is untouched — deliberately: a wrong number on a screen costs nothing, a wrong package size becomes a real bill, so the two consumers of that one estimate now get different trust thresholds. Admin/customer notifications and the `AccountEvent` audit trail now record both the raw and dampened figures when they differ (the raw-vs-dampened gap is exactly how this bug was diagnosed, so the audit trail keeps it visible going forward) and the customer-facing forward message drops the "equal to last month's average" claim when dampening changed the number, since claiming equality would be false in that case.

**Delegation and review:** root-caused independently, then design reviewed by a 5-model council (`flash`, `flash-medium`, `flash-3.7`, `claude-opus`, `pro` — unanimous on root cause and the dampening approach) before any code was written. Implemented by GLM 5.3 in an isolated worktree (48 turns, ~194 credits off-peak) against a precise spec; the resulting diff was independently re-verified (copied into the main tree, full backend suite re-run by hand, not just trusted from the worktree) and then separately re-reviewed by a 3-model implementation-specific council (`flash-3.7`, `claude-opus`, `flash-medium`) for bugs in the actual code (not the design) — unanimous: no blocking bugs. Two minor, non-blocking edge cases surfaced by `claude-opus` and left as known follow-ups: (1) a genuinely heavy user on a small package could repeat the same size indefinitely if every cycle stays under 5 days — safe-direction (under-provisioning) but operationally noisy; (2) the "repeat current size" branch re-floors through the pre-existing `_round_package_size`, which can shrink a non-multiple-of-5 custom package by up to a few GB on renewal — checked against live data: only 3 such package sizes exist fleet-wide (2/6/7 GB), and this rounding behavior already existed in `_round_package_size` before this fix, it's just newly reachable via the repeat branch.

**Verification before deploy:** GLM's own test run + an independent re-run of the full suite in the main tree: **24/24 backend scripts green**, including the new `test_auto_queue_dampening.py` reproducing both real accounts' exact numbers (mansoorizade → 20 GB queued, not 195; account 71 → 130 GB queued, not 225) plus a gradual-growth regression case (35→55→65 GB, none throttled) and the insufficient-data path (untouched). Secret-scan on the diff clean.
**Verification after deploy (live):** backend container recreated, containers up, 0 errors in logs; `/docs` and `/openapi.json` both 200; grepped the deployed container's own `sync_job.py` to confirm `BILLING_MIN_CYCLE_DAYS`/`MAX_GROWTH_MULTIPLE` are actually present in the running code, not just the build; watched **two live scheduled sync cycles execute successfully** post-deploy with zero errors.
