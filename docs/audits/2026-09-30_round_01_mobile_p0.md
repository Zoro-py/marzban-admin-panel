## ۴) رفع اعمال‌شده (`359cdaa`)

1. `lib/chunkRecovery.ts` — ‏`recoverableLazy`: هر ۱۴ صفحهٔ lazy روی شکست chunk-Load یک
   **reload خودکار یک‌باره** می‌کنند (گارد ۱۵ثانیه‌ای sessionStorage ضدحلقه)؛ reload روی
   index.html تازه (no-cache) می‌نشیند و خودش را درمان می‌کند.
2. `GlobalErrorBoundary` — پیام فارسی «نسخهٔ پنل به‌روز شده است» + دکمهٔ بارگذاری، فقط برای
   chunk-Load؛ + باندری بیرونی دور Suspense تا `/login` هم دیگر tree را به سفیدی نبرد.
3. نگهبان بوت در `index.html` — اگر خود entry کهنه باشد و اپ اصلاً mount نشود، بعد از ۴
   ثانیه بنر استاتیک فارسی «بارگذاری مجدد» ظاهر می‌شود (به‌جای سفیدصفحهٔ مطلق)؛ `main.tsx`
   با `__VPN_PANEL_MOUNTED__` آن را برمی‌دارد.

**راستی‌آزمایی:** ‏`tsc -b` + ‏`npm run build` تمیز؛ پروب Playwright (هارنس واقعی، ۳۹۰px):

## ۵) صادقانه باز: لایهٔ شبکهٔ موبایل

از این محیط نمی‌شود vantage واقعی دیتای موبایل ایران را شبیه‌سازی کرد — و همین دور یک نمونهٔ
زندهٔ همین جنس هم دید: SSH مستقیم همین لپ‌تاپ به فرانسه (بخش ۶) بعد از بنر RST می‌خورد در
حالی‌که HTTPS همان سرور سالم است؛ یعنی «یک مسیر/کلاینت به این سرور می‌رسد و دیگری وسط راه
کشته می‌شود» کاملاً واقعی است. اگر بعد از دیپلوی این رفع هم موبایل باز نشد، تست
تعیین‌کننده سمت مالک است: (الف) موبایل روی WiFi همان لپ‌تاپ — اگر باز شد، مشکل شبکهٔ موبایل
است نه کد؛ (ب) بعد از تلاش موبایل، لاگ access میزبان چک شود که آیا درخواست اصلاً رسیده یا
نه — نبودِ خط جدید = فیلترینگ/DPI اپراتور موبایل روی IP دیتاسنتر (برای پنلی که روی همان
سرور Marzban است دور از انتظار نیست) و راهش خارج از کد است (دامنهٔ میانی/CDN، پورت/IP
دیگر). **هیچ «رفع» ساختگی داخل کد برای این لایه ساخته نشد.**

## ۶) نکتهٔ عملیاتی ثبت‌شده — SSH فرانسه از مسیر مستقیم لپ‌تاپ

لپ‌تاپ را شامل نبود. یعنی RST بعد از بنر از یک لایهٔ میانی (احتمالاً فیلتر abuse خود VPS)
می‌آید نه از fail2ban سرور. **راه‌حل پایدار که در همین دور استفاده شد: `ssh -J vpn-detroit
root@95.182.83.238` (ProxyJump — TCP از IP دیترویت، احراز هویت همچنان کلید لپ‌تاپ، هیچ
کلیدی جابه‌جا نمی‌شود).** اگر دفعهٔ بعد SSH مستقیم فرانسه چنین کرد، مستقیم retry نکنید و از
